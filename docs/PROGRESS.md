## M2 — Mock PDP + API skeleton (started 2026-10-18, done 2026-10-18)

Plan §11: « `apps/mock-pdp` per §3; `apps/api` with auth, tenants, invoices CRUD, validate endpoint,
PdpAdapter wired to mock, pg-boss workers, webhooks. Acceptance: `scripts/run-scenario.ts happy` sends
10 invoices and reaches `paid` in < 60 s using the accelerated clock; `duplicate-send` scenario proves
idempotency. »

How each criterion is read here:

- **Mock PDP per §3**: `POST /invoices` (CII or UBL, same `@fi/core` validator), the scripted lifecycle
  in business time sped up by a factor, `POST /scenarios/:id`, `GET /invoices/:id/status`, signed
  webhook push when a webhook URL is set, `POST /inbound`, an injectable clock.
- **PdpAdapter wired to the mock**: the API only talks to `PdpAdapter`; a conformance suite in
  `@fi/pdp-adapter/contract` runs against the mock (and against the B2Brouter sandbox in M4).
- **Auth**: tenant API keys (`Bearer fik_…`, stored hashed) created by an admin token. Magic link
  belongs to the add-in (M3).
- **Accelerated clock**: one real second = `MOCK_PDP_SPEED` business seconds (default 86 400, a day per
  second), so the 32-day default lifecycle runs in about 32 s.
- **Idempotency**: the same invoice sent twice — same API request, double click, a retry after a lost
  answer — gives one deposit at the platform and one `deposited` transition.
- Scenarios run in-process (PGlite + both apps on ephemeral ports) so they are part of `pnpm verify`.

## M4 — B2Brouter sandbox (started 2026-10-18)

Plan §11: « Real adapter, sandbox contract tests green, status mapping, inbound polling. Acceptance: one
invoice goes Excel → B2Brouter sandbox → status visible in the sheet without manual steps. »

How each criterion is read here:

- **Real adapter**: `createB2BrouterAdapter` implements `PdpAdapter` on B2Brouter's documented API
  (`docs/B2BROUTER.md`, OpenAPI 2026-06-26): import the XML, then send it (never in one call); no blind
  retry of a POST (B2Brouter has no idempotency key for invoices): look the number up first, and reuse
  the invoice the platform already holds when its original file is ours byte for byte; directory lookup
  with the 202 polling; payment through `POST /accounts/{account}/payments`; webhook HMAC and both
  payload shapes. Every behaviour the docs leave open has a `TODO(verify)` pointing to
  `docs/B2BROUTER.md` §11.
- **Sandbox contract tests green**: `@fi/pdp-adapter/contract` (10 tests) runs on every `pnpm verify`
  against a local stand-in that speaks B2Brouter's documented protocol (both shapes where the docs
  disagree), and against the real B2Brouter sandbox with the owner's `test_` key, behind a manual flag
  (plan §9: « nightly, manual flag »).
- **Status mapping**: B2Brouter states → our platform statuses → state machine, in code with tests
  (`docs/B2BROUTER.md` §7); a state we do not know is kept raw on the timeline and changes nothing.
- **Inbound polling**: the sweep asks each company's platform for received invoices and stores each one
  once, unparsed; triage and the Réception screen are M6.
- **Credentials**: one operator key for the B2Brouter integration group (one key serves every account,
  `docs/B2BROUTER.md` §2), from the environment, never in the database or a log line; `FI_ENV=sandbox`
  accepts only `test_` keys.
- **Excel → sandbox → sheet without manual steps**: a company on B2Brouter sends an invoice from the task
  pane; the API imports and sends it; the webhook or the sweep brings the status back; the pane writes it
  in `FI_Statut` without a click. Proven by an E2E against the stand-in on every run, and against the
  real sandbox once the owner's key is set.

## M5 — Monitor + Collect + Report (started 2026-10-18)

Plan §11: « MonitorAgent, CollectAgent with chasing plans and email drafts, ReportAgent weekly, overdue
cron, k6 batch test. Acceptance: late-payment scenario produces the right chase steps on the right days
with the accelerated clock; mise en demeure is never auto-sent (test asserts it). »

How each criterion is read here:

- **Overdue cron**: a recurring job moves an invoice whose due date (Europe/Paris) has passed without a
  payment from `delivered`/`accepted` to `overdue` (actor `system`). It runs every few minutes and is
  idempotent, so a server that was down at midnight catches up.
- **CollectAgent, chasing plans, e-mail drafts** (plan §4 `chase_plans`, §6): once an invoice has reached
  the customer with a due date, its plan lists the steps of the company's cadence (default J-3 courtesy,
  J+1, J+8, J+15 firm, J+30 formal notice draft), each with its date. On its day, from 9:00 Paris, a step
  produces an e-mail draft in plain French (vouvoiement) whose number, amount and dates are written by
  code. The first step after the due date moves `overdue` → `chasing`. A step missed meanwhile is skipped,
  never sent late in a burst; a new cadence reschedules the steps not done yet. A payment (from the
  platform, or recorded by the user and reported to the platform as « Encaissée »), a write-off or a
  credit note ends the plan; a refusal or dispute pauses it; a payment promise recorded by the user holds
  the steps until its date. Drafts are deterministic templates: no model writes amounts or legal text.
- **Sending**: in Review mode (default) every step is a draft the user sends from their own mailbox
  (copy, or open in the mail app) and marks as sent. In Autopilot (opt-in per company, with an amount
  ceiling, plan §0.2) the agent sends the courtesy, reminder and firm steps itself through the
  deployment's mail service: never for a test invoice, never above the ceiling, never without a recipient
  address. **The formal notice (mise en demeure) is always a draft, whatever the mode** (plan §6).
  Autopilot covers chasing only; invoices still leave on « Envoyer ».
- **MonitorAgent** (plan §6): on every platform rejection or customer refusal, a note on the timeline says
  what to do next. For a rejection: the rule ids found in the platform's answer (deterministic) and « fix

  the customer, with a drafted message, chosen by a model after pseudonymization; all three options when
  the AI is off. It never resends and never changes a status. Prompt in `prompts/monitor.md`, with an eval.
- **ReportAgent weekly**: every Monday from 8:00 Paris, an e-mail to the company's owners (where the
  deployment has a mail service), and the same card in the task pane: at most 10 lines, numbers first
  (sent, paid, overdue, at risk), then the three things the user must do. Deterministic: the numbers and
  the priorities are facts computed from the invoices.

  invoices for one company against a local stack on a real Postgres and checks that each was deposited

  The run checks that each chase step

## M6 — Reception (started 2026-10-18)

Plan §11: « Screen 5, InboundAgent, accountant export (CSV + FEC-style), IBAN-change alert. Acceptance:
injected inbound invoices appear, duplicates flagged, export opens in a standard accounting tool without
errors. »

How each criterion is read here:

- **Screen 5 « Réception »** (plan §3): a tab of the task pane lists the supplier invoices the company's
  platform received, newest first: supplier, number, date, amount, due date, status (Nouvelle, Bonne pour
  paiement, Contestée, Exportée) and what the agent noticed, in plain French. Each one can be approved
  (« Bon pour paiement ») or disputed with a reason. « Exporter vers le comptable » makes the files of the
  approved invoices not exported yet; every export can be downloaded again.
- **InboundAgent** (plan §6): deterministic. When an invoice arrives, it reads the CII or UBL file, finds

  addressed to another company; duplicate (same supplier and number already received); possible duplicate
  (same supplier, amount and date under another number); amounts or VAT that do not add up (the EN 16931
  arithmetic and VAT rules of `@fi/core`); other rules the file breaks, for information; first invoice from
  this supplier; credit note; IBAN change. No model: nothing here needs judgment, and a model must not
  decide whether money goes out. An unreadable file, another company's invoice, a duplicate or amounts that
  do not add up cannot be approved, only disputed.
- **IBAN-change alert**: when a known supplier's invoice carries an IBAN that none of its earlier invoices
  had (disputed ones aside), the row shows an alert with the old and new IBAN (masked) and the advice to
  call the supplier on a number already known. Approving it requires ticking « J'ai vérifié ce changement
  auprès du fournisseur », and the audit records it. An IBAN whose checksum is wrong is flagged too.
- **Accountant export (CSV + FEC-style)**: one export takes the approved invoices not exported yet (test
  invoices only from Mode test, in files marked test) and makes two files: a CSV for a spreadsheet (`;`,
  UTF-8 with BOM, decimal comma, one line per invoice) and a purchase journal in the layout of the FEC of
  article A47 A-1 of the Livre des procédures fiscales (the 18 fields in order, tab separator, header line,
  AAAAMMJJ dates, decimal comma, UTF-8, entry numbers that continue from one export to the next), named
  `SirenFECAAAAMMJJ.txt`. It is a file to import, not the company's legal FEC, which only its accounting
  software can produce. The exported invoices become « Exportée ».
- **Injected inbound invoices appear**: in Mode test, « Recevoir une facture de test » (Normale, Doublon,
  RIB modifié) puts a synthetic supplier invoice from « Fournitures Démo SARL (test) » in the company's

  The API writes it as the test platform would deliver it, the same way on the mock and on B2Brouter

  mock's `POST /inbound` would tie it to the mock and to ids the mock restarts after a restart. Invoices
  the test platform itself delivers are test invoices too.
- **Duplicates flagged**: the second copy of an invoice (same supplier and number) is flagged « Doublon » and

- **Export opens in a standard accounting tool without errors**: the FEC file is imported by Paheko, an

  error, and the balance there matches the invoices. In `pnpm verify`, a checker asserts each rule of
  article A47 A-1 on the file, and the CSV is read back column by column.

## R0 — Groundwork for checking documents together (started 2026-10-19)

The next stages check each invoice against the company's other documents (orders, delivery notes,
purchases) in the background, and let the user talk with an agent about what was found. R0 makes the
current sheet path cheap enough to run all the time and gives those checks their first tables.
Criteria, written here before the work:

- **Customer settings reach the rules**: a confirmed customer carries two switches in Clients,
  « Exige son numéro de bon de commande » and « Organisme public »; every check of an invoice to that
  customer passes them to the rules, so FF-PO-01 and G2.32 follow the customer instead of always running
  with the defaults (today one never fires, the other always does). Changing a switch checks that
  customer's invoices not yet sent again. The third, « Livré à une autre adresse » (BR-FR-14), waits:
  it asks for a delivery address the sheet cannot give yet (`docs/DEFERRED.md`).
- **Numbering history in proportion**: the history rules (BR-FR-CO-02, FF-NUM-01, FF-NUM-02, FF-CN-01)
  receive, for each invoice, only the earlier invoices that decide them. Same verdict as with the whole
  list (property test on random histories); checking 5 000 invoices of one series costs about what it
  costs without history (measured before: 0.9 s without, 8.7 s with).
- **A sync that changes nothing writes nothing**: the sheet's invoices are read in one query and computed
  in memory; an invoice is written only when its content, its customer or its rows changed, and checked
  again only when something its verdict depends on changed (content, customer switches, company
  setting, the day, its numbering neighbours). Test: a repeat sync issues 0 INSERT/UPDATE/DELETE; one
  cell changed → one invoice updated and checked.
- **Rows that move keep their invoice**: a row inserted above an invoice without a number (key `row:N`)
  no longer hands that invoice to its neighbour: an invoice found unchanged elsewhere in the sheet
  follows its rows.
- **Registry, first tables**: `docs`, `doc_lines` and `items` hold every outgoing invoice (test ones
  flagged) and every received invoice that could be read, line by line: item references (BT-155/156/157),
  quantity, unit, net price, discount, net amount, VAT, order line (BT-132), and the source cell of a
  sheet invoice. An item is the company's, found by its article reference, else by its normalized name.
  A per-company queue job (`registry.refresh`: one running and one waiting per company) fills them after
  a sync that changed something and after a received invoice; the sweep catches up what is missing. The
  RGPD export and deletion cover the new tables.
- **Mapping fields**: « Référence article » (BT-155) and « Remise » (line discount amount, BT-136) can
  be mapped, by detection or by hand, and reach the invoice and the registry.
- **Load test**: `pnpm load:sync` (in-process, PGlite, or a throwaway Postgres with `--database-url`)
  measures the first sync of a 5 000-row sheet, a repeat sync (0 writes), a one-cell edit (1 invoice
  written), and the registry projection of 50 000 lines (target < 30 s). Results recorded here.
- **Docs**: `docs/ARCHITECTURE.md` stops saying the pane validates (it never called `validate()`);
  `docs/DEFERRED.md` lists the registry tables later stages bring (`row_state`, `layout_profiles`,
  `sources`, `links`, `findings`, `rule_exceptions`) and the sweep split per company.

## R1 — Every sheet of the workbook (started 2026-10-19)

R0 gave the registry its tables and filled them with invoices. R1 lets the company's other sheets in:
customer orders, delivery notes, purchases, price lists. An agent reads a layout it has never seen, the
user confirms it in the pane, and from then on every edit of that sheet reaches the registry. Nothing is
checked against them yet (R2). Criteria, written here before the work:

- **Four kinds of sheet**: `packages/core` reads a sheet of customer orders (« Commandes »), delivery
  notes (« BL »), purchases (« Achats ») or a price list (« Tarifs ») into registry documents: number,
  date, customer or supplier (name, SIREN), the order a delivery note delivers, and lines (article
  reference, designation, quantity, unit, unit price, net amount in cents, VAT rate, source cell). A row
  it cannot place is counted, never guessed. A dictionary proposes the kind (sheet name, headers) and the
  columns, as `detectMapping` does for invoices.
- **LayoutAgent**: an extension of MappingAgent (same masking, budget, orchestrator and guardrails),
  prompt `packages/agents/prompts/layout.md`. It sees the headers and about twenty rows, pseudonymized,
  and answers the kind and the columns, each with a confidence; it is called only when the company has
  no profile for those headers. AI off or failing: the dictionary answers, and the pane says so.
- **Eval**: 20 layouts (5 orders, 5 delivery notes, 5 purchases, 5 price lists, each with a trap), scored
  on the key fields (the kind, number, date, customer or supplier, article reference, designation,
  quantity, unit price): ≥ 95 % with a live model, recorded and replayed by `pnpm verify`; the
  dictionary's score recorded as the floor.
- **Layout profiles**: `layout_profiles` keeps a confirmed layout per company (fingerprint of the
  headers, kind, columns → fields, who confirmed, version); a sheet with known headers, in any workbook,
  is recognized without calling the model.
- **Confirmation in the pane**: a sheet is read only after the user confirmed its kind and columns
  (« Inclure cette feuille »), columns under 0.8 marked « à confirmer ». `sources` keeps each included
  sheet with the date of that consent; « Retirer » deletes its documents from the registry.
- **Events on every included sheet**: while the workbook is open, each included sheet is followed by its
  own change event and read once when the pane opens. An edit in « Commandes » reaches the registry in
  one sync: API test (one cell changed → one document written again; the same sheet again → 0 writes)
  and pane test (typing in « Commandes » while « Factures » is the active sheet syncs « Commandes »).
- **Screen « Registre »**: one card per source (kind, rows, documents, last change, rows not understood),
  the invoice sheet included; the workbook's other sheets, those whose name suggests a kind first, with
  « Inclure »; a click on a document selects its cell in the workbook. The tableau de bord points to
  sheets that look like orders, delivery notes, purchases or price lists and are not included yet.
- **Audit and RGPD**: including, confirming, removing and every read that changed the registry write an
  audit event; the export and the deletion of a company cover `layout_profiles` and `sources`;
  `docs/RGPD.md` lists the new processing.
- **Docs**: `docs/ARCHITECTURE.md` (what R1 added, its decisions), `docs/DEFERRED.md` (what waits),
  `docs/AI_PROVIDERS.md` (the LayoutAgent eval).

## R2 — Checks across documents (started 2026-10-20)

R1 brought the company's orders, delivery notes, purchases and price lists into the registry. R2 reads
them against the invoices: a deterministic Linker ties each invoice to the order it bills, a Checker
runs rules on documents together, and what it finds — always a rule in code, with the money at stake
and the cells that prove it — can stop a send. Criteria, written here before the work:

- **Linker**: an invoice is tied to its order by the order number (BT-13 on the invoice, the sheet's
  « N° commande »; score 1.0), else by customer + article + quantity within a window of dates (lower
  score); a delivery note to its order the same way. One candidate links on its own; several stay
  « proposée » until a person confirms one, and a confirmed or rejected link is never undone by the
  Linker. Table `links` (kind billed_by / fulfils, score, method number / item / similarity / human,
  status auto / proposed / confirmed / rejected).
- **Rules inside an invoice**: A1 HT and TTC confused (an amount ≈ quantity × price × (1 + rate), or a
  price ≈ the order's or the price list's × (1 + rate)); A2 a total typed as a number instead of a
  formula that no longer matches (the pane sends which cells hold a formula, not the formulas); A3 a
  discount applied twice, or a percentage typed as an amount; A4 a VAT rate that is not this article's
  usual one; A5 a price that differs from the price list (« Tarifs »).
- **Rules across documents**: B1 invoiced less than the order for the same quantity, the rest invoiced
  nowhere → « N € non facturés » (blocking); B3 delivered but not invoiced after 30 days (warning); B4
  invoiced more than ordered or delivered (blocking); B5 the same order lines in two invoices, or
  invoices and advances above the order (blocking); B6 customer or SIREN differs from the order
  (warning). Each finding has its amount at stake in cents, its cells, a fingerprint; the list is sorted
  by money. Table `findings`.
- **When it runs**: in the company's registry job, after the registry is brought up to date (an invoice
  synced, a sheet read, received invoices); before a send, the checks run again on what is current. A
  test invoice is checked against the sheets like a real one, never added to the real ones.
- **Send gate**: in Review, an open blocking finding turns « Envoyer » into « Envoyer quand même »: the
  pane lists the findings and asks for a confirmation, the API refuses a send that does not name them,
  and the send writes an audit event with them. The autopilot never sends an invoice with an open
  blocking finding: its send is cancelled with the reason on the timeline, and the invoice waits for
  « Envoyer ».
- **Screen « Contrôles »**: the open findings, largest amount first, each with its explanation in plain
  French (templates in `fr.json`; ExplainAgent's wording later), « Corriger la ligne » (selects the
  cell), « Voir la commande », « Ouvrir la facture »; the links waiting for a person, with « Oui » /
  « Non ». The invoice's fiche shows its findings.
- **Corpus**: at least 30 scenarios with their expected findings, among them 300 € / 400 € (order C-118
  10 × 40 €, invoice F-2026-042 10 units for 300 € → B1 100 €); every rule has a scenario where it fires
  and one where it does not; API test: the autopilot does not send with a blocking finding.
- **Audit and RGPD**: a check run that opened or closed findings, a link confirmed or rejected, and a
  send despite findings write audit events; the export and the deletion of a company cover `links` and
  `findings`; `docs/RGPD.md` lists them.
- **Docs**: `docs/ARCHITECTURE.md` (what R2 added, its decisions), `docs/DEFERRED.md` (what waits).

## R3 — Purchases and margin (started 2026-10-20)

R2 checks what is sold against what was ordered and delivered. R3 adds what it cost: the supplier
invoices received through the platform and the « Achats » sheet give each sold article its purchase
price, and rule B2 says when a sale loses money or falls under the company's margin. Criteria, written
here before the work:

- **Suppliers**: a supplier invoice received through the platform (not a « Mode test » one) puts its
  supplier in `parties` (kind supplier, source « invoice », found by SIREN; one already there is not
  changed). A supplier never shows in « Clients » and the customers' API cannot change one. The
  « Registre » screen counts the suppliers recognised.
- **What it cost**: each sold line of an invoice (not a credit note, not an advance) takes its cost from
  a purchase of the same article — a received invoice's line or a row of an included « Achats » sheet.
  The same article: the company's own reference on both sides (BT-155 sold, BT-156 bought), else the
  same name once accents, case and punctuation are set aside; a different unit or currency is not the
  same article (« pièce », « unité » and « each » — C62, H87, EA — are one unit: an invoice built from a
  sheet says C62 where suppliers say H87). The purchase is the latest one on or before the sale's date, else the first one in the
  60 days after it. The tie is a `links` row of kind « cost » (purchase → invoice); a « Non » on it
  makes the next purchase count. A test invoice takes its cost from test purchases and the sheets, a
  real invoice never from a test purchase.
- **B2**: sold under its cost → « vente à perte N € » (blocking: « Envoyer quand même », the autopilot
  stops); sold above its cost but under the margin the company set in « Réglages » → warning, with the
  euros missing to reach it. No margin set: no margin warning. Changing the margin checks again.
  « Voir l'achat » selects the purchase's row in « Achats », or opens the supplier invoice in
  « Réception ».
- **Acceptance** (architecture document, R3): « sold under its cost » is caught from a supplier
  invoice received from the mock platform, and from the « Achats » sheet. The 300 € / 400 € example
  with the supplier's 10 × 35 € gives B1 100 € and B2 50 €.
- **Corpus**: B2 fires and stays quiet in its own scenarios (cost from a received invoice, from the
  « Achats » sheet by name, the margin warning, the latest purchase, test purchases kept apart, a
  rejected cost, another unit).
- **Audit and RGPD**: the margin setting is audited with the other settings; suppliers and cost links
  are in the company's export and its erasure; `docs/RGPD.md`, `docs/DEFERRED.md` and
  `docs/ARCHITECTURE.md` updated.

## R8 — Chat and edits (started 2026-10-21)

R2–R3 find what does not add up and point at the cells; the person still corrects the sheet by hand.
R8 lets them ask « pourquoi ? » about a finding, have the cell corrected, and take the correction back,
all in the pane. Criteria, written here before the work:

- **A correction the code builds**: a finding whose correction is one price in the invoice's sheet (an
  invoice billing less or more than its order — B1, B4 —, a price other than « Tarifs » — A5 —, a price
  with the VAT on top — A1) carries it: the cell, the value it holds, the value it should hold, taken
  from the order or the price list. Never from a model. A finding the code cannot correct says so, and
  the chat gives the steps instead.
- **« Avant → Après » and one click**: every correction, asked in the chat or from the finding's card,
  shows the cell, what it holds and what it will hold, and changes nothing before « Appliquer ». Before
  writing, the pane checks that the cell still holds « Avant » and is not a formula; otherwise it writes
  nothing and says why.
- **The journal**: one `edits` row per cell: the invoice, the finding, the conversation, the sheet and
  address, the value before (and its formula), the value after, who asked (agent or person), the status
  (proposed, applied, declined, reverted, conflict) and its times. Every step writes an audit event.
- **Taking it back**: « Annuler la correction », or asking the agent, writes « Avant » back when the
  cell still holds « Après », with the same card and click. If the person changed the cell since,
  nothing is written: the pane says what the cell holds now and asks; writing over it takes another
  explicit click.
- **A sent invoice**: an invoice already sent through the platform, or on its way, is never edited:
  the correction is refused and the answer proposes an avoir (or a facture rectificative) that cites
  its number and date, with the amount.
- **Confirmed by the checks**: after « Appliquer » the sheet is synced and the invoice checked again;
  the agent says « corrigé » only when the finding is resolved, otherwise it names what remains.
- **The chat**: on a finding, « Demander à l'assistant » opens a conversation tied to it and kept in
  Postgres; its first message is the finding's own wording, shown at once. The agent (ToolLoopAgent of
  `ai` 7.0.143) reads through tools — the finding, a document, an article's history — and every amount
  comes from code; it corrects and takes back only through `proposeFix` and `undoEdit`, which the pane
  carries out. Everything sent to the model is pseudonymized and the answer re-hydrated. AI off: no
  chat, and the card's correction works without it.
- **Document lock**: while a correction of invoice X waits for its click (five minutes at most), the
  background leaves X alone — its findings stay as they are, the autopilot does not send it — and checks
  and sends the other invoices as usual. The click (applied, declined, conflict) ends the lock and X is
  checked at once.
- **The background goes on**: a chat turn does not take one of the orchestrator's two background slots
  of the company; while the model answers, another invoice's sync, checks and autopilot run.
- **Eval** (architecture document, R8): « expliquer → corriger → annuler » on the 300 € / 400 € example:
  the agent explains with the finding's figures and invents none, calls `proposeFix` on that finding,
  says it is corrected only once it is resolved, and calls `undoEdit` on that correction. Recorded on a
  live model, replayed by `pnpm verify`; the prompt hash ties the recording to `prompts/chat.md`.
- **Audit and RGPD**: conversations and edits are in the company's export and its erasure;
  `docs/RGPD.md`, `docs/DEFERRED.md`, `docs/ARCHITECTURE.md` and `docs/AI_PROVIDERS.md` updated.

## R4 — Microsoft 365 (2026-10-21)

R1 reads the other sheets of the open workbook, and only while it is open. R4 reads files the company
keeps in OneDrive or SharePoint, on the server, when Excel is closed. Nothing changes for a company that
does not connect: the connector asks for a sign-in, a file chosen by name, and « Inclure cette feuille »
for each sheet. Criteria, written here before the work:

- **Sign-in from the pane**: « Connecter OneDrive » signs in with the Microsoft account of the person
  (nested app authentication of MSAL.js where Office has it, else the Office dialog), personal or work.
  Only `Files.Read` and `User.Read` are asked, which need no administrator. The pane hands our API a
  token for our API only; the API exchanges it on behalf of the person and keeps the refresh token
  sealed (AES-256-GCM), never in clear, never sent back to the pane. Sources and dates of every
  Microsoft behaviour in `docs/MICROSOFT365.md`; what only a real account can settle is a TODO(verify).
- **Files chosen, not the drive**: the person picks files in Microsoft's own File Picker (OneDrive or
  SharePoint, .xlsx, .xlsm or .csv). The API reads only those: never a folder, a search or the rest of
  the drive. Each sheet of a picked file is proposed like a sheet of the open workbook (R1: a profile
  already confirmed, else LayoutAgent, else the dictionary) and read only after « Inclure cette
  feuille ».
- **Read without Excel**: the API downloads the file and reads it itself (.xlsx parts, .csv in UTF-8 or
  Windows-1252); sizes are capped before anything is inflated. The same snapshot twice writes nothing,
  as for a sheet of the open workbook.
- **Changes noticed**: the API checks each picked file's content tag every few minutes; on a personal
  OneDrive a Graph subscription tells it sooner (the notification has no content: it only starts the
  check). A changed file is read again, its documents are checked again (R2–R3), and the findings show
  in the pane — the file was never opened. A subscription is renewed before it expires, removed when the
  connection is.
- **Calm when it breaks**: a file deleted, moved out of reach, too large or unreadable says so on its
  row in « Registre »; a connection Microsoft no longer honours asks the person to connect again; the
  documents already read stay until then. Microsoft's limits (429, Retry-After) are respected.
- **Disconnecting deletes**: « Déconnecter OneDrive » (and « Retirer » on one file) removes the tokens,
  the subscription, the files, their sheets and every document read from them; the findings that
  rested on them are resolved by the next check.
- **Scout**: when the open workbook itself is in OneDrive or SharePoint (its address), or the company's
  mail domain is served by Microsoft 365 (its MX record), the pane proposes the connector once; it never
  connects by itself.
- **Acceptance** (architecture document, R4): a file in a test OneDrive (personal and work) changed →
  a finding in the pane, the file never opened; disconnecting deletes the data. Against the Microsoft
  stand-in (`apps/mock-pdp`, `/microsoft`) in `pnpm verify` and in the E2E; on real accounts once the
  owner registers the application (`docs/RUNBOOK.md`).

## R7 — Patterns and learning (started 2026-10-22)

R2–R3 compare a document with the one that should agree with it; R7 compares an invoice with the
company's own habits, and learns from what the person answers. Criteria, written here before the work:

- **B7, an unusual price**: an invoice line's unit price far from what this customer usually pays for
  this article — the median of its earlier lines (the last 12, at least 3, same unit), more than 20 %
  away and more than four times their usual spread — is a warning with the usual price, how many
  invoices say it and the money at stake (at least 1 €). An hour billed at a day's price, or a day at an
  hour's, is caught. A line an order or « Tarifs » prices stays with B1, B4 and A5.
- **« C'est normal »**: on a finding about a price (A5, B1, B2, B4, B7) the person says it is normal,
  for this customer and this article or for this article whatever the customer, for 3 months, 12 months
  or with no end. The exception is kept (`rule_exceptions`: the rule, the customer, the article, the end,
  who and when) and audited; the finding resolves and the same rule on the same customer and article is
  not found again until the end — the invoice it held is no longer held. « Contrôles » lists the
  exceptions; « Retirer » brings the finding back.
- **Article synonyms**: an article sold with no purchase to give it a cost, and an article bought whose
  name looks like it (same unit), are proposed « Est-ce le même article ? » in « Contrôles ». « Oui »
  ties them (`item_synonyms`) and every rule reads them as one article from then on (B2 finds the cost);
  « Non » never proposes the pair again. Both audited.
- **Money not invoiced in the weekly report**: the report says what the checks found billed short in
  the week — findings first seen in the last 7 days on real documents (B1, B3, A3, a loss under B2, a
  price under A5 or B7) and still open — with the amount; no line when there is none.
- **Audit and RGPD**: exceptions and synonyms in the company's export and erasure; `docs/RGPD.md`,
  `docs/DEFERRED.md`, `docs/ARCHITECTURE.md` updated; corpus scenarios for B7 firing and quiet.

## §6 VIES — EU customers' VAT numbers (started 2026-10-24)

Plan §6 gives the PartyAgent a `vies.check(vat_id)` tool; M7 and M8 left it out (`docs/ONBOARDING.md`
§4, `docs/DEFERRED.md`). An intra-EU supply (K) or an EU reverse charge (AE) is exempt from French VAT
only if the customer's VAT number is valid in its own country, and VIES (the European Commission's
public service) is where a seller checks it. Criteria, written here before the work:

- **Checked without a click**: an invoice not yet sent, with a K or AE breakdown and a customer VAT
  number (BT-48) of another EU member state, has that number checked in VIES within one sweep (5
  minutes by default), once a day per number at most, one request at a time. The company's own VAT
  number goes as the requester, so VIES can return a consultation number. French numbers stay with
  DGFiP's list; numbers outside VIES' member states are never sent.
- **Proof kept**: every answer (valid or not, the name and address VIES gives, its consultation
  number, the day) is kept with the company's account and written on the invoice's timeline.
- **An invalid number is said plainly**: a number VIES says is not valid gives a warning on the
  customer's VAT number (FF-VIES-01): what VIES said and when, why it matters (no exemption without a
  valid number), what to do. A warning, not an error: VIES can lag a new registration, and the
  person decides.
- **Calm when VIES cannot answer**: busy, unavailable, timed out or blocked: nothing is stored,
  nothing is said against the invoice, the next sweep tries again; no invoice waits for VIES.
- **Deterministic core**: the rule reads the stored answer from its context; core makes no network
  call; the answer is part of the check key, so the same answer gives the same verdict and a new one
  checks the invoice again.
- **Audit and RGPD**: each check writes an audit event; the answers are in the account export and
  erased with it; `docs/ONBOARDING.md`, `docs/RGPD.md`, `docs/DEFERRED.md`, `docs/RULES.md` updated,

## Memory M0: the vault and its schema (started 2026-10-25)

`docs/plans/memory.md` § M0, `docs/DECISIONS.md` D12. Criteria, written before the tests:

- **A page** is a Markdown file a person can read: YAML frontmatter checked by its type's Zod schema
  (amounts « 12400.00 » in the file, cents in code), the text, then a `## Liens` section code writes
  from the links. The same page always gives the same bytes.
- **`compile`** takes a patch of pages and writes all of it or nothing: a frontmatter that breaks its
  schema, a page in the wrong folder, `rh/` while it is off, a source that does not exist, a link to
  no page: nothing is written at all. Links are written both ways; the section indexes, the root
  index, the log and the open questions follow in the same write. A patch that changes nothing
  writes nothing.
- **A crash** (`SIGKILL`) at any moment of a compile never leaves a damaged file; after recovery the
  patch is there whole or not at all, and the hashes of what was written match the files.
- **A person's edit wins**: a page edited in the last minute is not written by an agent's patch (an
  open question says so instead); an agent never replaces a text a person wrote in, it may only add
  a paragraph.
- **A person's edit is read**: the page checked and indexed, its backlinks written on the other
  pages, a line in the log, the person's file left as they typed it; an unreadable page leaves the
  index with an open question; a deleted page leaves the index.
- **`rebuild`** reads every page again: indexes, `_schema.md` and backlinks written from them; an
  invalid or misnamed page out of the index with a question; a synchronisation's conflict copy moved
  to `_conflicts/`; a vault of a newer schema refused. 1 000 pages in under 60 s.
- **One writer**: a second runner is refused while the lock is held; a lock past its time, or left
  by a process of this machine that is gone, is taken over.
